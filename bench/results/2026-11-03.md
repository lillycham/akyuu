# Replica performance and SSH experiment, 2026-11-03

SSH correctness checks passed between two machines. Performance acceptance
remains open. A 5,000-entry store caused a busy writer on the M4. Linux
archive measurements reached the experiment deadline.

The product code was commit `3acd6a0`. These experiments changed no product
code and used no live memory store.

## Method

The Mac had an Apple M4 and 16 GiB RAM. The Linux machine was a MacBook Air
(M1, 2020), with 7.33 GiB visible RAM, Asahi/NixOS and Linux 7.1.5.
The machines differ in hardware and operating system. These results do not
isolate an operating-system effect.

Both used GHC 9.10.3 and the same synthetic fixture generator. The library
used the Cabal development build. The benchmark driver used `-O2`, two RTS
capabilities and a 2 GiB heap cap. CLI measurements used the Mac development
executable and the native Linux Nix package.

The fixtures had 100, 1,000 or 5,000 base entries. One quarter were topic
revisions across at most 32 refs. The rest formed a log. Summaries covered
batches of 20 older episodes. Bodies had a marker and 1,000 padding characters.
The 5,000-entry base inventory held 5,189 objects and about 6.06 MB of payloads.
Two control memories and summary objects account for the extra objects.

Local metrics have five observations. Their clocks exclude process startup
and include result evaluation. CLI clocks include startup. Reads use ordinary
filesystem caches. No cache flush occurs. Initial archive population differs
from later checks of an existing archive. Initial sync and join each have
one observation. Unchanged sync has three observations.

The initial Mac pilot overlapped the SSH experiment. It is excluded here.
The recorded Mac run had no competing experiment workload. Linux ran its
own local fixture and bare remote. Normal system activity was not controlled.

The Linux 5,000-entry aggregate run reached its 120-second command deadline
during archive measurements. A second run used a separate process per metric.
It saved the four completed metrics above. Its archive series also reached
the 120-second deadline. This bounds the whole five-sample invocation,
including setup. It does not establish the duration of one archive call.
The driver then stopped that profile. It did not measure its remaining steps.

Both failed runs remain in the raw records. The split process mode changes
GC history and setup between metrics. Cross-row comparisons remain exploratory.

### Concurrent writes

Two independent direct commits started at a shared barrier. The harness
checked accepted event IDs against each reported outcome.

At 5,000 entries on the M4, one write returned `RepositoryBusy` after 1,107 ms.
The other write succeeded after 1,604 ms. Accepted state matched both results.
Both writes succeeded at 100 and 1,000 entries on each machine. The Linux
5,000-entry run stopped before this test.

The direct-commit timer encloses lock acquisition, the transaction and release.
It approximates the uncontended mutation-lock window. The busy result gives
separate behavioural evidence of contention. Independent refs avoid a stale
version as the explanation for that result.

## SSH correctness

The Mac replica used Git over authenticated SSH to a temporary bare remote
on Linux. The Linux replica used that remote through its local path.
The experiment verified:

- A fresh join received a distinct replica identity.
- Offline topic alternatives survived until explicit resolution.
- DAG branches, a joining append and exact summary evidence converged.
- A missing remote preserved pending work and `CURRENT`. Retry published it.
- A pin restored an archived object after GC on both replicas.

The unavailable-remote test moved only the temporary bare repository.
It did not simulate packet loss. The harness removed its local and remote
fixtures. Its timing log is diagnostic because it overlapped the excluded
Mac pilot. HTTPS authentication and network interruption recovery remain open.

## Implication

Performance acceptance is not met. The source shows full event and payload
validation in `loadSnapshot`. `transact` repeats inventory work under the
mutation lock. `archiveSnapshotWith` also holds that lock throughout the
durable archive copy. Sync repeats complete inventory operations.

These paths explain plausible scaling costs. No CPU profile or syscall trace
was collected, so their individual shares remain unmeasured.

The first target is the archive lock boundary. Prepare immutable archive data
without blocking ordinary writers. Keep publication and GC checks explicit.
Concurrent GC and crash tests must preserve the current durability guarantees.
Then profile repeated validation and unchanged sync before the next optimisation.
A larger lock retry timeout alone would preserve the long blocked interval.
